## 修复前已确认问题

### 1. 切换页签后，分流出口回退到第一轮缓存（P1）

- 位置：`src/views/home/split-results.tsx:45`、`:66`、`:184`。
- `round` 保存在组件局部状态，切换页签会卸载组件，返回后重新从 0 开始；缓存 key 包含该轮次。
- 浏览器可控样本：第一轮全部回显 `8.8.8.8`，点击重新检测后全部回显 `1.1.1.1`。切换到 CDN 再返回分流出口，页面重新显示 `8.8.8.8`，最新的 `1.1.1.1` 消失。
- 影响：用户重新检测得到的新结果，在普通页签切换后被旧结果替代。
- 建议：为检测会话保存当前轮次，或使用稳定的最新结果缓存并显式刷新；不要把组件挂载次数与测量轮次混用。

### 2. DNS/CDN 重新请求失败后，旧成功数据覆盖当前失败（P1）

- CDN：`src/views/cdn/index.tsx:120` 保留旧 `data.node` 与当前 `error`；`src/views/egress/cdn-lanes.ts:126` 和 `src/views/egress/cdn-stage.tsx:200` 只判断 `node && !loading`，仍把旧节点计入成功。
- DNS：`src/views/dns-exit/index.tsx:28` 在请求结束后优先选择 `query.data`，同一查询重新请求失败时，这里仍是上次成功数据，覆盖当前轮次的 `progress.data`。
- 可控复现使用真实 TanStack Query `QueryObserver`：CDN 请求状态为 `error`、旧节点为 `SJC`，聚合仍输出 `kind=exit`、`samples=1`；DNS 当前进度为 21 次全部失败，最终却选择旧数据，显示失败 0 次并保留旧解析器。
- 真实入口：页签卸载后重新挂载同一缓存 key，触发过期查询重新请求。
- 建议：明确区分本轮结果与历史结果；本轮失败优先进入失败统计，历史数据不得计入本轮成功数。

### 3. DNS/CDN “重新检测”没有同步刷新 HTTP 对照地址（P2）

- 位置：`src/views/cdn/index.tsx:135`、`src/views/dns-exit/index.tsx:91`。
- 点击重新检测只更新节点/DNS 的轮次，HTTP 探针与归属查询使用固定 key，没有显式重新请求。
- 浏览器可控样本：CDN 已从 `SJC` 更新为 `LAX`，HTTP 对照仍显示之前的 `8.8.8.8`，没有使用新网络样本的 `1.1.1.1`。
- `staleTime` 只决定缓存是否过期，不会自动在 60 秒后启动请求，因此不能假设旧地址只会保留 60 秒。
- 建议：一次重新检测应统一更新相关探针，并按同一检测轮次组装对照信息。

### 4. 网易 DNS 地区解析把未知和海外默认归为中国（P2）

- 位置：`src/views/dns-exit/api.ts:97`。
- `nstoolCountry` 只识别港澳台，其他所有输入都返回 `CN`。
- 可控复现：`{ dns: "8.8.8.8" }` 被解析为 `country_code: "CN"`；添加 `dns_province: "美国"` 后得到 `geo: "CN · 美国"`。
- 客户端 HTTP 地址也使用同一个解析函数，错误国家可继续影响对照出口分类。
- 建议：仅对明确识别的地点赋国家；缺失或无法识别的地点保持未知，海外地点保留其真实国家信息。

### 5. 超时重试把首轮网络耗时算成排队时间（P2）

- 位置：`src/views/home/api.ts:168`、`:197`。
- 重试复用首次调用的 `queuedAt`，`queueWaitMs = startedAt - queuedAt` 因而包含第一次实际请求的耗时。
- 单源、无队列竞争的可控复现：首轮耗时约 120ms 后抛超时，第二轮成功；结果却记录 `queueWaitMs=124`、`networkMs=36`、`totalMs=160`。
- 影响：实际 8 秒超时重试可被显示成约 8 秒排队，站点请求耗时只剩最后一次请求，误导瓶颈判断。
- 建议：按尝试分别记录入队、开始和结束时间，再合并队列与网络耗时，保留重试次数。

### 6. CDN 厂商数量按分组数重复计算（P2）

- 位置：`src/views/egress/cdn-stage.tsx:203`、`src/views/egress/cdn-lanes.ts:112`。
- 线路 key 是 `path:family`，国内/海外属于不同分组；页面把成功线路数直接当作厂商数量。
- 使用现有目录全部成功的可控样本：21 个入口、16 个不同 `family`，实际产生 19 个成功分组，页面会显示 19 家厂商。Cloudflare、字节跳动和网宿被跨分支重复计算。
- 建议：厂商统计按成功结果的 `family` 去重；分支数量与厂商数量分别计算。

### 7. DNS 分组的国家、城市和 IP 可能来自不同成员（P2）

- 位置：`src/views/egress/dns-lanes.ts:207`、`:309`。
- `pickGeo()` 从信息最完整的成员选择位置文本，却从第一个具有国家码的成员选择国家；之后又将 `geo.ip` 覆盖成分组代表 IP。
- 可控复现：成员 A 是 `CN · Cloudflare`，成员 B 是 `United States, San Jose · Cloudflare`；分组输出 `country_code: CN`、`country: United States`、`city: San Jose`，IP 又来自成员 A。
- 影响：同一条聚合记录会组合互相矛盾的国家、城市与地址，不能作为某个解析器的完整归属。
- 建议：代表 IP 与其归属必须来自同一成员；多地点分组不能通过拼接字段生成单一地点。

## 统计口径观察（不列为确定缺陷）

DNS 来源的 `source.samples` 是各解析器 IP 出现次数之和。一个来源请求 3 次，每次返回两个解析器时，来源观察次数会是 6，探测请求次数仍是 3。当前文案是“观察次数”，并未明确声称这是请求次数，因此该行为本身不能直接判为重复计算错误；后续若要统计请求成功率，必须新增按请求计数的字段，不能直接使用这个值作分子。
